# 千面·OneKOS｜下一阶段落地 OnePage

> 目标不是再给销售顾问增加一套复杂工具，而是让顾问既可以在 OneKOS Web 中直接操作，也可以直接与飞书 Aily 对话、由 Agent 代为执行同样的操作；两种方式共用同一套后端和飞书多维表格数据。

## 一、当前基础与最终形态

### 1. 当前已经具备的能力

| 模块 | 当前情况 | 真实边界 |
|---|---|---|
| OneKOS Web | 已跑通“动态画像—选题—内容包—四重质检—模拟发布—评论转线索—确认学习”的演示链路 | 本地运行；未配置飞书或外部模型时会明确进入模拟模式 |
| 飞书 Aily | 已加入测试群，并连接团队共享的飞书多维表格，可按顾问、任务、内容和线索查询记录 | 当前主要负责读取和解释，尚未直接调用 OneKOS 后端 |
| 飞书多维表格 | 已设计顾问档案、画像标签、品牌知识、内容任务、内容成果、评论线索、反馈事件七类业务表 | 是 Aily 与 Web 的共享协作数据底座；正式数据仍需补齐权限、有效知识和关联关系 |
| OneKOS 后端 | 已提供运行状态、上下文读取、内容生成、评论分析和反馈确认接口 | 当前监听本地地址，缺少面向公网调用的身份认证、任务状态和运营监控 |
| 内容模型 | 后端支持 OpenAI-compatible 外部模型；未配置时使用本地确定性生成器 | 模型只负责提出候选内容，不能绕过服务端规则直接写 Base |
| 抖音与 CRM | 已用结构一致的模拟评论、线索和销售反馈展示闭环 | 未获得正式平台权限和账号授权，不能描述为实时数据或自动发布 |

### 2. 最终产品架构

```text
                              销售顾问
                         ↙                 ↘
                OneKOS Web                 飞书 Aily
              顾问直接操作页面        顾问对话，Agent 代为操作
                         ↘                 ↙
                 查询 / 发起任务 / 补充输入 / 确认 / 查看结果
                                  ↓
                         OneKOS 统一业务后端
       上下文查询 / 画像 / 路由 / 模型调用 / 四重质检 / 线索 / 学习
                                  ↕
                         共享飞书多维表格
          顾问 / 画像 / 知识 / 任务 / 内容 / 评论线索 / 反馈结果

外部数据回流：抖音授权数据 / CRM 授权结果 → OneKOS 后端同步与校验 → 共享飞书多维表格
```

Aily 和 Web 不是两套不同职能的产品，而是操作同一套 OneKOS 能力的两种交互方式。使用 Web 时，顾问通过页面按钮和表单直接调用后端；使用 Aily 时，Agent 先理解顾问的自然语言，再代为调用相同的查询、生成、质检、确认等后端接口，并把执行结果回答给顾问。两种入口的业务能力、状态流转、人工门禁和最终结果保持一致，差异只在于“顾问直接操作”还是“Agent 代为操作”。

外部兼容模型不构成独立业务分支，而是 OneKOS 后端在内容生成环节调用的内部能力。模型返回的结果必须先回到后端，经过字段校验、事实检查和四重质检后，才能作为内容成果写入共享飞书多维表格。抖音评论、互动数据以及 CRM 试驾/成交结果同样先由后端同步和校验，再写入评论线索或反馈事件表，作为后续线索识别和画像学习的依据。

## 二、后续安排

竞赛时间有限，优先完成能够证明方案成立的核心链路：Aily 与 Web 使用同一后端、共享同一份飞书多维表格，任务能够被发起、执行、质检、写回并再次查询。其他能力按当前问题继续补齐。

| 模块 | 当前情况 | 主要问题或局限 | 下一步修改 |
|---|---|---|---|
| 共享飞书多维表格 | 已有七张业务表，Aily 能读取对应记录 | 部分数据仍为演示数据，跨表关系和真实写回链路需要进一步核对 | 统一顾问、任务、内容和线索 ID，跑通至少一条从任务生成到内容成果写回的真实链路 |
| Aily | 已能在飞书群中查询 Base 并回答 | 目前还不能调用 OneKOS 后端完成生成、质检和状态推进 | 将后端提供给 Aily 技能/API 调用；若当前配置受限，则先用 Base 指令队列完成任务触发和结果回读 |
| OneKOS Web 与后端 | Web 已能调用后端展示生成、质检、评论和反馈流程 | 当前主要运行在本地，与 Aily 仍是两段演示 | 让 Aily 与 Web 调用同一套业务接口，并确保两端看到相同任务 ID、内容状态和结果 |
| 内容创作室 | 已输出标题、开场、脚本、分镜、素材清单、剪辑时间轴和评论预案 | 目前以文字内容包为主，距离可直接拍摄和快速成片仍有距离 | 完善素材补充、版本对比、质检问题定位和成片预览，并规划接入图像生成和视频剪辑能力 |
| 四重质检与矩阵检测 | 已有事实、合规、人设和矩阵检查逻辑 | 演示样本量有限，问题说明和阻断结果还需在界面与 Base 中保持一致 | 补齐代表性样本，明确展示碰撞内容、阻断原因、修改建议和最终门禁状态 |
| 评论线索与指标看板 | 已能用模拟评论展示字段提取、A/B/C 分级和人工接管 | 尚未接入真实抖音数据，指标主要用于演示 | 先稳定模拟/人工导入链路和 Base 写回，再补内容采用率、近重复率、线索数量和顾问负担指标 |
| 抖音 | 发布、评论和互动数据均未正式接入 | 受应用审核、账号授权和接口权限影响，短期内不适合作为主链路前置条件 | 当前继续人工发布和模拟/人工导入数据；获得授权后再由后端同步数据并写回共享 Base |

### 1. 优先完成 Aily 与 Web 主链路

目标链路为：

```text
顾问通过 Web 直接操作，或与 Aily 对话发出任务
                         ↓
                 OneKOS 同一套后端
                         ↓
       读取共享 Base → 执行生成与质检 → 写回结果
                         ↓
          Web 展示结果 / Aily 查询并回答结果
```

当前 Aily 已能读取飞书多维表格，但还不能直接调用后端完成内容生成、评论分析和反馈确认。下一步优先将 OneKOS 后端提供给 Aily 技能/API 调用，由 Aily 传入顾问 ID、任务 ID、内容 ID 和具体动作；后端完成读取、生成、质检与写回后，再把结构化结果返回 Aily。

如果当前 Aily 配置暂时无法直接调用自定义 API，则采用 Base 指令队列作为演示兜底：Aily 写入一条带任务 ID 和状态的指令，后端读取并执行，结果写回 Base，Aily 再读取并回复。两种方案都复用现有后端和共享数据，不在 Aily 中另建业务逻辑。

### 2. 完善内容创作室

当前内容创作室已经能够生成完整文字内容包，下一步重点是让内容从“可读”进一步接近“可拍、可剪、可确认”：

- 增加顾问真实素材补充区，把每段口播、实车镜头、路线记录与分镜逐项对应。
- 增加版本对比和局部修改，保留模型原稿、顾问轻改稿和最终确认稿。
- 将四重质检问题定位到具体标题、脚本句子或分镜，并支持修改后重新检查。
- 增加成片预览与素材完成度，让顾问明确还缺哪些镜头、字幕和事实证据。

### 3. 引入图像生成大模型和视频剪辑 Skill（计划延伸）

图像生成大模型用于生成封面草图、分镜参考图、示意背景和视觉风格方案，帮助顾问在拍摄前理解画面；不得用生成图冒充真实车辆状态、真实门店、顾问经历或客户案例。生成资产需要标注 AI 生成，并将提示词、版本和关联内容 ID 写入素材记录。

视频剪辑 Skill 接收顾问上传的真实视频素材，根据内容包中的分镜和剪辑时间轴自动完成粗剪、字幕、封面、片段排序和节奏建议，输出“待顾问确认”的成片草稿。顾问仍需检查真实画面、车型信息、字幕事实和最终发布内容。

这两项属于内容创作室的后续增强能力，不作为当前主链路完成的前置条件。当前先在文档和界面中预留素材资产、生成状态和成片版本字段，后续接入具体模型或 Skill 时仍复用同一内容 ID 和 Base 数据结构。

### 4. 补齐质检、评论线索与指标展示

- 四重质检：补充事实引用、违规表达、人设证据和矩阵碰撞的代表性案例，确保 Web 展示和 Base 记录一致。
- 评论线索：继续使用明确标注的模拟或人工导入评论，跑通“评论进入—字段提取—A/B/C 分级—顾问接管—反馈写回”。
- 指标看板：展示内容准备时间、轻改采用率、矩阵近重复率、内容数量和 B 级以上线索数量；当前演示指标必须标明模拟或试点目标。

### 5. 抖音接入的局限与可行方案

当前项目中的抖音发布、评论、点赞、收藏和分享数据均为模拟。正式接入受开放平台应用审核、接口权限和顾问账号授权影响，因此不把它作为当前主链路完成的前置条件，也不能在演示中描述为实时正式数据。

当前可行方案是：内容由 OneKOS 生成和质检后，仍由顾问手动进入抖音完成最终发布；评论和互动数据继续使用明确标注的模拟数据或人工导入数据验证分析链路。获得正式权限后，再由 OneKOS 后端同步授权账号的作品、评论和互动数据，校验后写入共享飞书多维表格，并与对应顾问和内容 ID 关联。无论是否获得发布接口，最终发布和高意向线索接管都保留顾问确认。

## 三、顾问最终操作链路与工具

### 1. 顾问看到的完整流程

```text
选择操作方式
Web：顾问在页面直接操作
Aily：顾问提出需求 → Agent 理解意图 → 代为调用同一后端 → 回答执行结果
                         ↓
首次使用
授权资料 → 系统生成并解释画像 → 顾问确认或纠偏
                         ↓
每天开始
查询“今天拍什么” → 系统推荐 1—3 个任务 → 顾问选择
                         ↓
内容准备
统一后端生成内容包并质检 → 顾问补真实素材、轻改并查看结果
                         ↓
发布前
系统展示事实引用与四重质检 → 顾问处理风险项并最终确认
                         ↓
发布
顾问手动发布，或在获得权限后明确确认一键提交至抖音
                         ↓
发布后
授权评论/模拟评论进入 OneKOS → 后端提取证据并分级 → 系统提醒 A 级线索
                         ↓
销售跟进
顾问人工接管 → 记录试驾/成交结果 → 顾问确认学习 → 下一轮画像和选题更新
```

以上每一个 OneKOS 业务节点都可以由顾问在 Web 中直接操作，也可以通过 Aily 对话让 Agent 代为查询或执行；例如“生成这个任务”“补充这段素材说明”“确认进入质检”“查看 A 级线索”。顾问日常只承担四个不可替代的决策：**选择任务、补充真实素材、最终确认、接管高意向线索**。查询状态、读取多张表、整理脚本、生成分镜、初步质检和评论归类由系统完成。

### 2. 顾问会用到哪些工具

| 工具 | 顾问是否直接使用 | 用途 | 使用频率 |
|---|---|---|---|
| 飞书群＋Aily | 是，对话式操作入口 | Agent 理解顾问指令，代为完成与 Web 相同的查询、发起、补充、确认和结果返回 | 按顾问偏好使用 |
| 飞书机器人卡片 | 是，轻交互 | 选择/拒绝任务、确认画像、接管线索、记录结果 | 节点触发 |
| OneKOS Web 工作台 | 是，可视化操作入口 | 顾问通过页面直接完成与 Aily 相同的查询、发起、补充、确认和结果查看 | 按顾问偏好使用 |
| 抖音 App/授权发布页 | 是 | 拍摄、检查成片、最终发布、必要时人工运营评论 | 每条内容 |
| 飞书多维表格 | 通常不需要直接打开 | 保存画像、知识、任务、内容、线索和反馈，供运营查看 | 顾问低频、运营高频 |
| CRM/试驾系统 | 视企业接入方式 | 记录正式跟进、试驾和成交结果 | 有线索时 |

## 四、核心亮点与落地可行性

| 亮点 | 与普通 AI 写稿工具的差异 | 当前落地基础 | 后续可行路径 |
|---|---|---|---|
| 动态内容 DNA | 不用固定人设概括顾问；每个标签都有权重、置信度、来源和证据 | 已有顾问档案、画像标签和确认后学习逻辑 | 接入授权历史内容、语音与采用/拒绝事件，持续更新而非一次画像 |
| “事实核＋人格壳” | 品牌事实与个人表达分开治理，避免模型编造参数和经历 | 后端只读取有效知识，缺事实会留待实拍补充 | 总部维护版本化知识表，过期/冲突自动阻断，价格权益人工复核 |
| “一题千解”与回声室治理 | 不只做同义词改写，而是按问题、地域、场景、证据和矩阵空白重新路由 | 已有画像匹配、矩阵样本和近重复检测 | 扩大真实矩阵样本，以选题、结构、视觉和 CTA 形成内容指纹 |
| 完整内容包 | 不只交付一段文案，还包含脚本、分镜、素材、字幕、剪辑时间轴、评论预案和 CTA | Web Demo 已能生成候选并执行质检 | 模型保持可替换，业务格式和质量门禁沉淀在 OneKOS 后端 |
| Aily＋Web 等价双入口 | 同一业务既可由顾问在 Web 直接操作，也可由 Agent 根据对话代为操作，结果完全一致 | Aily 已能读共享 Base，Web 已跑通业务流程 | Aily 连接同一后端接口；不可用时用 Base 指令队列兜底 |
| 评论转销售线索 | 每个城市、车型、购车时间和试驾意愿都保留原文证据 | 已有评论分析、A/B/C 分级和人工接管状态 | 先人工导入，再申请抖音评论权限；CRM 结果授权后回流 |
| 人工门禁 | AI 不自动发布、不自动私信、不承诺价格、不擅自学习 | 代码和提示词均保留发布、A级线索和画像学习确认 | 将门禁固化为后端状态机和审计日志，不依赖模型自觉 |
| 单后端、共享数据 | Aily 与 Web 不复制逻辑，避免结果不一致 | 已有统一服务、Base Repository 和业务主键 | 公网部署后两个入口共用 API、幂等键、质检规则和状态 |

总体可行性来自三个方面：

1. **技术上可渐进：** 当前代码已经将数据仓储、模型客户端、业务服务、质检引擎和 HTTP API 分层；部署、鉴权和异步任务可以逐步补齐，不需要推倒重做。
2. **业务上可先验证：** 即使 Aily 后端调用、抖音和 CRM 权限尚未完成，也可以用共享 Base、人工发布和模拟/人工导入数据验证内容采用率、顾问负担和线索证据质量。
3. **风险上可控制：** 外部模型只生成候选，品牌事实由有效知识控制，所有正式发布、客户触达、高意向线索和画像学习均保留人工确认。

> OneKOS 的最终价值不在于“多生成几篇文案”，而在于把总部事实、顾问个性、内容生产、平台反馈和销售结果组织成一套可解释、可确认、可持续学习的业务系统，同时让顾问日常只面对最少、最自然的操作。
