# OneKOS 一体化 MVP 集成设计

## 1. 目标

在保留现有 OneKOS Web 演示与飞书 Aily 顾问入口的基础上，以现有「千面·OneKOS 运营中台（演示）」多维表格作为统一数据底座，新增 Node 服务端数据适配层与 OpenAI 兼容的大模型适配层，打通以下链路：

顾问画像 → 任务路由 → 内容生成 → 四重质检 → 顾问确认 → 模拟评论回流 → 线索分级 → 人工接管 → 反馈确认 → 画像权重更新。

除真实抖音账号与 CRM 外，其余环节均须可运行、可回读、可演示。所有顾问、评论、互动和线索数据持续标注为模拟数据。

## 2. 已确认边界

- 飞行社内置 Aily/OpenClaw 团队智能体仅保留为飞书内顾问交互入口；当前租户未开放 OpenAPI 渠道，Web 服务不依赖该智能体的外部 API。
- Web 服务使用外部 OpenAI 兼容模型完成内容生成、评论分析和画像调整建议。
- 多维表格由服务端通过飞书 OpenAPI 读写；模型无权直接读写 Base。
- 不接入真实抖音、CRM 或试驾系统；评论、点赞、转发、试驾意向和销售结果均为模拟输入。
- 不自动发布、不自动私信、不自动加微、不自动预约试驾、不承诺价格或权益。
- 高意向线索和画像权重变化必须由人工确认。
- 现有未提交的「飞书落地中心」UI改动属于用户工作，必须保留。

## 3. 架构

```text
浏览器 Web MVP
  ├─ GET  /api/demo/state
  ├─ POST /api/content/generate
  ├─ POST /api/comments/analyze
  └─ POST /api/feedback/:eventId/confirm
            ↓
OneKOS Node 服务
  ├─ OneKOSService：业务编排与状态门禁
  ├─ FeishuBitableClient：读取/写回飞书多维表格
  ├─ OpenAICompatibleClient：调用外部大模型
  ├─ QualityGate：事实、合规、人设、矩阵质检
  └─ SimulationRepository：未配置外部凭证时的演示兜底
            ↓                         ↓
飞书多维表格（统一状态）         外部大模型 API（仅生成）
```

### 3.1 运行模式

系统提供三种显式模式，不允许静默降级：

1. `live`：飞书与模型均已配置，读取真实 Base 中的模拟业务记录，调用外部模型并写回。
2. `hybrid`：飞书可用但模型未配置，读取 Base，使用确定性本地生成器，页面显示“模型模拟”。
3. `simulation`：飞书和模型均未配置，使用仓库内固定数据，页面显示“全链路模拟”。

接口响应必须包含 `mode`、`simulation`、`warnings`，让评委能分辨真实连接与演示兜底。

## 4. 模块职责

### 4.1 配置模块

从环境变量读取配置并进行非敏感校验。密钥只存在于本机 `.env`，仓库只提交 `.env.example`。

关键变量：

- `FEISHU_APP_ID`
- `FEISHU_APP_SECRET`
- `FEISHU_BASE_APP_TOKEN`
- 七张业务表的 `table_id`
- `LLM_BASE_URL`
- `LLM_API_KEY`
- `LLM_MODEL`
- `LLM_TIMEOUT_MS`

### 4.2 飞书适配器

使用 `tenant_access_token` 调用飞书多维表格 OpenAPI。适配器只负责：

- 获取并缓存访问令牌；
- 按业务主键查询记录；
- 列出非空业务记录；
- 创建或按 `record_id` 更新记录；
- 将飞书错误转换为稳定的应用错误。

写入必须先按内容ID、线索ID或事件ID查询，命中后更新，未命中才创建，避免重复。

### 4.3 外部模型适配器

调用 OpenAI 兼容的 `chat/completions` 接口。模型接收服务端整理后的最小上下文，不接收飞书密钥、Base Token或无关记录。

适配器负责：

- 超时和取消；
- 提取模型响应文本；
- 去除 Markdown 代码围栏；
- 解析并校验 JSON；
- 对无效输出返回明确错误，不伪装成功。

### 4.4 OneKOSService

业务服务承担四个用例：

1. `getAdvisorContext(advisorId, taskId)`：汇总顾问档案、有效画像标签、待办任务与有效品牌知识。
2. `generateContentPackage(input)`：调用模型，执行四重质检，按内容ID写回内容成果。
3. `analyzeCommentLead(input)`：提取字段证据、计算线索等级，写回评论线索与反馈事件。
4. `confirmFeedback(eventId)`：人工确认后更新标签权重，并保留原值、新值和证据。

### 4.5 回声室检测

MVP使用可解释的本地算法，不增加向量数据库：

- 标题和开场采用归一化 token Jaccard 相似度；
- 内容结构提取“结论开场/参数口播/实测记录/家庭叙事/问答”等结构指纹；
- 选题按目标车型、用户问题、地域场景和内容角度统计覆盖；
- 达到阈值时阻止自动通过，并返回需要补位的矩阵空白。

结果写入矩阵质检分与问题列表，演示中展示“相似表达去重”与“空白场景重路由”的区别。

## 5. 数据契约

所有API统一返回：

```json
{
  "success": true,
  "mode": "live",
  "simulation": true,
  "data": {},
  "warnings": [],
  "error": null
}
```

失败时 `success=false`，`error` 包含稳定错误码与可读说明；不得返回伪造业务数据。

### 5.1 内容生成输入

- `advisorId`
- `taskId`
- `contentId`

服务端自行从 Base 获取画像和知识，前端不得提交品牌事实正文来绕过知识库。

### 5.2 内容生成输出

- 选题理由
- 开场、脚本、分镜、素材清单、标题、评论预案、转化动作
- 事实引用与缺失事实
- 四重质检分、问题和是否通过
- 写回动作与 `record_id`

若真实素材缺失，状态只能是“待顾问补真实素材”。

### 5.3 评论分析输入

- `commentId`
- `contentId`
- `advisorId`
- 原评论与模拟互动数据

### 5.4 评论分析输出

- 城市、家庭结构、车型、购车时间、试驾意愿
- 每个字段的原文证据
- 线索分、等级和人工跟进建议
- 下一条内容选题
- 评论线索与反馈事件 `record_id`

模型可以提出线索分建议，最终等级由服务端确定性规则复核。

## 6. 前端体验

保留现有七页导航，在顶部增加数据连接状态：

- `飞书已连接 / 飞书模拟`
- `外部模型已连接 / 模型模拟`
- 最近同步时间

关键按钮形成一条可演示路径：

1. “读取今日任务”加载 ADV-017 与 TASK-001；
2. “生成内容包”展示阶段状态并写回内容成果；
3. “模拟评论回流”创建 COMMENT-DEMO 数据；
4. “识别并写回线索”展示 A 级人工接管；
5. “顾问确认学习”将 EVENT-DEMO 的建议权重应用到 TAG-004；
6. 返回画像页展示更新前后差异和证据来源。

调用超过 90 秒时显示可取消状态；失败时保留上次成功结果，不以成功动画掩盖错误。

## 7. 安全与合规

- `.env`、访问令牌和模型密钥不得进入Git或浏览器响应。
- 服务端限制请求体大小和允许的API路径。
- 品牌事实只来自状态有效且在有效期内的知识记录。
- 模型输出中的数值若无法匹配事实库，事实质检不得通过。
- 模拟数据在页面、API和写回记录中均标记为模拟。
- 日志不得打印密钥、完整Token或用户隐私字段。

## 8. 测试策略

使用 Node 内置测试框架和依赖注入，不新增测试框架。

- 配置测试：模式判断、缺失密钥与秘密脱敏。
- 飞书适配器测试：令牌缓存、查询、创建、更新、API错误。
- 模型适配器测试：成功JSON、代码围栏、超时、非法JSON、HTTP错误。
- 服务测试：画像汇总、内容写回查重、品牌事实门禁、线索证据、人工确认更新。
- 回声室测试：近重复、结构重复、空白角度补位。
- API测试：状态码、统一契约、请求校验和静态资源兼容。
- UI契约测试：连接状态、操作按钮、模拟标识和错误提示存在。

测试默认使用内存替身，不依赖网络。另提供显式的手工联调命令验证飞书和模型，不在常规 `npm test` 中访问外部服务。

## 9. 完成标准

- `npm start` 一条命令启动；
- `npm test` 全部通过；
- 未配置任何密钥时仍可运行确定性演示；
- 配置飞书后可回读已存在的 CONTENT-DEMO-001、LEAD-DEMO-001 与 EVENT-DEMO-001；
- 配置外部模型后可生成结构化内容并经服务端门禁写回；
- 画像反馈必须人工确认后才改变权重；
- 3—5分钟内可完整展示业务闭环；
- 现有用户未提交改动和无关文件保持不变。
