# OneKOS 顾问画像初始化服务设计

## 1. 目标

把现有“预置模拟顾问”升级为可实际使用的顾问首次初始化服务。顾问通过 3 分钟轻量资料完成冷启动，系统结合基础资料、表达偏好、历史内容和语音转写生成候选画像；只有经过顾问确认的标签才能成为画像 V1，并参与后续选题、内容生成和学习闭环。

本阶段完成后，应能从一个尚无画像的顾问开始，连续走通：

`选择或创建顾问 → 收集资料 → 生成候选画像 → 顾问确认 → 写入飞书 Base → 生成首条任务 → 进入机会雷达`

## 2. 比赛版边界

### 2.1 包含

- 飞书入口使用会话中可获得的用户标识映射顾问；Web 演示允许选择已有顾问或创建模拟顾问。
- 基础资料、至少三组表达偏好、可选历史内容和可选语音转写。
- 模型分析与本地规则降级。
- 带维度、权重、置信度、来源和证据的候选标签。
- 顾问删除、修改、降权、锁定和确认标签。
- 初始化会话持久化、失败重试和幂等确认。
- 画像 V1、标签证据、授权信息和首条任务写入。
- 初始化完成后进入现有机会雷达、内容生成、质检和线索闭环。

### 2.2 不包含

- 独立飞书 OAuth 登录页、复杂租户管理和企业组织同步。
- 自动抓取未经授权的社交平台内容、评论、私信或通讯录。
- 自动发布、自动联系客户或自动预约试驾。
- 未经顾问确认直接生效的画像推断。

生产版身份、组织和权限能力只保留接口边界与落地说明，不在本次比赛实现范围内。

## 3. 初始化方式

采用“轻量冷启动 + AI 候选画像 + 顾问确认 + 后续持续学习”。

| 阶段 | 必要输入或操作 | 系统输出 |
|---|---|---|
| 身份确定 | 飞书用户映射，或 Web 选择/创建模拟顾问 | 稳定 `advisorId` |
| 基础资料 | 城市、门店、从业年限、目标用户、至少一个擅长问题 | 显式事实 |
| 偏好采集 | 至少三组表达偏好 | 冷启动风格信号 |
| 样本增强 | 最多五条历史内容、可选语音转写、禁用表达 | 个性化证据 |
| 候选生成 | 顾问点击生成 | 候选标签与证据 |
| 人工确认 | 修改、删除、降权、锁定并确认 | 生效标签集合 |
| 初始化完成 | 服务端校验并写入 | 画像 V1 与首条任务 |

历史内容和语音不是必填项。缺少样本时仍可初始化，但相关标签置信度必须降低，并显示“待后续证据校准”。

## 4. 状态模型

顾问初始化状态：

`uninitialized → collecting → pending_confirmation → active`

初始化会话状态：

`draft → generated → confirming → confirmed`

异常状态包括 `generation_failed` 和 `write_failed`。失败会话保留输入、候选标签和写入进度，可在同一 `sessionId` 上重试，不重复创建顾问、标签或任务。

取消会话只关闭当前草稿，不删除已经生效的历史画像。

## 5. 数据设计

### 5.1 顾问档案

在现有顾问档案中补充：

- `初始化状态`
- `当前画像版本`
- `身份来源`：`feishu` 或 `demo`
- `外部用户标识`：可选，不向前端公开敏感凭据
- `授权状态`
- `首次初始化时间`

### 5.2 画像标签

每个标签保存：

- `tagId`、`advisorId`、`profileVersion`
- `dimension`、`label`
- `weight`、`confidence`
- `sourceType`、`sourceRefs`
- `evidence`
- `status`：候选、生效、锁定、废弃
- `createdAt`、`updatedAt`

模型不得把车型价格、政策或参数当成顾问画像证据。历史文案只能证明表达与专长倾向，不能成为品牌事实来源。

### 5.3 初始化会话

新增“画像初始化会话”数据集合，并在飞书 Base 落地为第八张表，保存：

- `sessionId`、`advisorId`、`status`
- 输入快照与授权选项
- 候选标签快照
- 顾问确认的标签及修改值
- 生成方式：模型或规则降级
- 写入进度与最近错误
- 创建、更新、确认时间

### 5.4 首条任务

确认画像后，以 `TASK-{advisorId}-001` 为稳定业务键幂等创建首条任务草案。任务只能引用已确认标签，不包含模型臆测的品牌事实，状态为“待生成”。

## 6. 服务接口

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/advisors` | Web 演示选择现有顾问 |
| `POST` | `/api/advisors` | 创建模拟顾问身份 |
| `POST` | `/api/onboarding/sessions` | 创建或继续初始化会话 |
| `GET` | `/api/onboarding/sessions/:sessionId` | 恢复初始化进度 |
| `POST` | `/api/onboarding/sessions/:sessionId/generate` | 生成候选画像 |
| `POST` | `/api/onboarding/sessions/:sessionId/confirm` | 确认标签并完成写入 |

确认接口接收标签 ID 及允许修改的 `label`、`weight`、`locked` 字段。服务端使用会话中的原始证据和顾问 ID，禁止客户端替换证据、来源或归属关系。

所有写接口返回统一错误结构，并支持客户端提供幂等键。公开响应不返回飞书 Secret、模型 API Key 或外部平台敏感标识。

## 7. 候选画像生成

### 7.1 模型路径

模型接收经过最小化处理的资料和授权样本，输出固定 JSON Schema。服务端负责：

1. 校验维度白名单；
2. 限制权重和置信度为 0—100；
3. 验证每个标签必须有输入证据；
4. 合并语义重复标签；
5. 删除敏感属性和品牌事实推断；
6. 给每个候选标签生成稳定 ID。

### 7.2 降级路径

模型未配置、超时或输出无效时，使用本地确定性规则生成基础候选画像。页面明确显示“规则降级生成”，但初始化流程仍可继续。

## 8. Web 交互

画像页按三个连续区域呈现：

1. **选择/创建顾问**：已有顾问可继续，首次顾问进入初始化。
2. **3 分钟资料采集**：基础资料、偏好、历史文案、语音转写和禁用表达。
3. **候选画像确认**：逐项展示权重、置信度、来源和证据，允许修改、删除、降权和锁定。

确认成功后展示画像 V1 摘要，并提供唯一主操作“生成首条任务并进入机会雷达”。刷新页面后应能通过会话接口恢复未完成初始化。

## 9. 写入一致性与异常处理

飞书 Base 不提供跨表事务，因此采用会话状态和幂等 upsert 保证最终一致：

1. 将会话标记为 `confirming`；
2. 按业务键保存顾问档案；
3. 保存已确认画像标签；
4. 保存首条任务；
5. 将会话标记为 `confirmed`；
6. 任一步失败时记录 `write_failed` 和已完成步骤；重试时只补未完成部分。

前端不得在服务端确认完成前显示“初始化成功”。重复点击确认必须返回同一画像版本和任务，不产生重复记录。

## 10. 测试与验收

### 10.1 自动化测试

- 服务测试：输入校验、候选标签、证据约束、规则降级、人工确认和幂等重试。
- Repository 测试：模拟仓库及飞书字段映射、初始化会话恢复和部分失败补偿。
- API 测试：完整路由、非法状态转换、统一错误和敏感信息保护。
- UI 契约测试：顾问选择、资料表单、候选标签确认、失败提示和恢复入口。
- Smoke：新顾问初始化 → 画像 V1 → 首条任务 → 内容生成 → 质检 → 线索 → 人工确认学习。

### 10.2 人工验收

- 无历史内容的顾问可通过偏好完成初始化，低置信度提示正确。
- 有历史内容和语音转写时，候选标签能引用具体输入证据。
- 取消标签后，该标签不写入 Base、不参与首条任务。
- 模型不可用时降级流程仍可演示。
- 页面刷新后可恢复未确认会话。
- 重复确认不会创建重复顾问、标签或任务。
- 经用户授权后，在测试飞书 Base 执行一次真实写回验收。

## 11. 与现有代码的关系

实现沿用当前 `OneKosService`、API Router、Simulation/Feishu Repository、运行模式和前端单页结构，不引入新的前端框架或数据库。现有 `feishu-poc` worktree 中未提交的初始化草稿仅作为需求参考，不直接合并；所有代码在 `feat/advisor-onboarding-service` 上按测试驱动方式重新实现。

## 12. 完成定义

- 新功能分支基于最新 `main`，工作树干净。
- 新增测试先失败，再通过最小实现修复。
- `npm run check` 全部通过。
- 初始化、降级、恢复和幂等流程均有测试证据。
- 文档、飞书字段清单、导入包和演示手册同步更新。
- 用户验收前不合并 `main`、不推送远端。
